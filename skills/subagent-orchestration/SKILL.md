# 团队任务编排

主代理应以用户目标、工作区范围和验收标准为输入，按已配置团队的实际职责选择流程。团队阶段与每个 task prompt 才是成员分工；目标字符串只是各任务共享的背景。

## 当前 task 工具 schema

只按本轮提供的工具定义调用。当前 `task` 工具支持：

| action | 参数 | 用途 |
| --- | --- | --- |
| `teams` | 可选 `team` | 查询团队介绍或指定团队详情 |
| `team_run` | `team`, `goal` | 按团队当前保存的阶段与任务定义执行 |
| `team_assign` | `team`, `stageId`, `taskId`, `member` | 管理员团队中重派已存在的任务 |

旧版说明中出现的 `create`、`send`、`read`、`stop`、`del`、`list`、`roles`、`pipeline` 并非当前 `task` 工具 schema，不得照搬或臆造。

## 必须先拆分的情形

对于需要多个阶段或多个专业职责的代码实现、故障定位与修复、调研/审查/验收任务：

1. 调用 `task(action="teams")` 查看已有团队介绍，选择职责与任务匹配且可运行的团队。
2. 调用 `task(action="team_run", team="…", goal="…")`。goal 写简明目标、范围和验收标准，不要粘贴整段对话。
3. 依靠团队内已配置的阶段任务提示实施职责拆分、依赖和验收；不能把用户原文直接作为某成员唯一的任务指令。
4. 核对团队真实终态和交付证据后再报告。团队没有覆盖分工或无法运行时，说明具体缺口并独立完成可推进部分，不伪造分派结果。

简单、原子任务可由主代理直接完成。不要读取或要求输出成员名册、成员提示词或内部消息；不要绕开团队工具直接把主任务交给单个角色。

## 团队配置不足时

- 先检查团队介绍和任务描述，不读取私有角色正文或内部会话。
- 只有实际工作需要多个交付时才选择多阶段团队，不为了“看起来有并行”而派多个团队。
- 保持用户目标、文件范围、不可变更项和验收标准短而明确。
- 对团队运行错误保留错误码和具体阶段，不重复提交同一目标造成多个并行流程。
- 若用户明确要求主代理自己完成简单工作，不强制调用团队。
- 若某个独立检查能并行减少等待，优先选择一个含该职责的已有团队，而不是把全任务原样塞给单个成员。
- 角色名称只作职责匹配，不代表其权限、运行环境或测试能力。
- 主代理应检查团队是否返回成功终态、必需阶段是否执行、结果是否与用户验收点对应。
- 失败或超时不等于成员已完成；记录现有进度与未交付内容，再决定是否继续。
- 不能修改团队配置时，指出缺失的阶段或具体任务，不要把未拆分状态包装成已完成。
- 团队目标可概括用户请求，但不能删除范围、关键约束、终止条件和可验证验收标准。
- 仅传递团队共同需要的上下文，不传入无关对话历史或不相关个人信息。
